4. How far the compiler looks

(i) The straight run (built, recommended)

Fire when an OPEN ALL FILES follows an unconditional CLOSE ALL FILES with nothing between that can change the path. In the walker: the CLOSE sets a flag; any label clears it (a sentence label, an IF's OTHERWISE and join labels); so do GO TO, STOP RUN and END. A DO does not, since control returns. This is the same boundary at which the register cache already clears (procedure.dart:422, “A label ends the straight run”).

Every path to the OPEN passes the CLOSE, so the one false alarm is a CLOSE ALL that closed nothing. It misses a CLOSE inside a DO'd procedure, every loop, and any IF between the two, even one with no transfer in it: the IF's join label ends the run. Corrected 2026-10-25: the first version named only the DO and the loop. 18 lines. To widen later: replace the flag.

(ii) Text order anywhere

Fires on correct programs. START. GO TO INIT. / FINI. CLOSE ALL FILES, STOP RUN. / INIT. OPEN ALL FILES, … GO TO FINI. never reopens, but its OPEN follows the CLOSE in the text. At severity 4 that forbids the run of a legal program. Not recommended at any severity above 1.

(iii) Control flow: every path to the OPEN passes a CLOSE ALL

Exact for its question, and adds the DO case. It needs a flow graph over GO TO, IF, DO and AT END that the generator does not build; 947's walk covers DO edges only. It still misses the likeliest real reopen, a loop (LOOP. OPEN ALL FILES … CLOSE ALL FILES. GO TO LOOP.), because the first entry does not pass the CLOSE. Only a “some path” check catches the loop, and that one can fire on paths the data never takes.

Named OPEN. OPEN file refuses today (an OPEN naming files (notes section 7)), so the sub-question has no site. For the record: J binds “files closed by this form”, so a named OPEN of a file that was not open at the CLOSE ALL is not forbidden by the text. STOP RUN's own close-all is not counted: nothing follows STOP RUN in a straight run.
