The three courses, and what each costs

A — the narrow set. Taken.

Build only what a run reaches. What it costs: the M7 diff pass gets a narrower comparison. M7 opens the sealed 1963 processor and measures our reconstruction against it; an entry we never wrote is an entry with no reconstruction to measure. What it costs to reverse: build the missing entries later from the same manual contracts. Nothing is thrown away.

B — the whole M4-17 set

Write all 130 now as tested handlers with no caller. CLAUDE.md section 11 permits that: its table marks the not-exercised, tested case permitted, provided "the code needs a concrete plan to get a caller. Record the plan in the design record that asks for the code." RT-1 carries that plan already, so the route was open.

What it costs: 102 handlers written from manual contracts that do not describe the algorithm. The three contract reports in evidence/ grade each entry against a printed key — evidence/s4-contracts-b1.md line 87: "FULL = the entry states its calling sequence, its effect, and where control resumes. PARTIAL = class pair and parameter encodings stated, algorithm not. NAME-ONLY = the entry body states only the family pairing". PARTIAL is the common verdict. Eight entries grade FULL, and every one of them has its protocol printed rather than its algorithm: the two pointer cells SYS)132 and SYS)133, which are memory and have no algorithm; the four MOVPAK dispatch entries SYS)179 to SYS)182, whose whole content is which pointer cell the calling sequence sets; and the two figurative movers SYS)243 and SYS)244, which write one repeated character.

Two further costs. The only test such a handler can carry is a decision-conformance test, which asserts what we decided and nothing else, so 102 handlers would add 102 tests that check our own reasoning against itself. And REVIEW.md humanness finding 3 — "Dead weight that the section 11 blocker does not already catch: code a test asserts on but no run reaches" — would attach to every one of them.

What it costs to reverse: deleting a hundred handlers and a hundred tests, and re-deleting them each time a reviewer asks why they are there.

C — the narrow set plus all of MOVPAK

MOVPAK is the move-and-convert package, SYS)179 to 258 and 267 to 282: 96 of the 130. Course C is course B minus the scaling and comparison routines. It carries the same costs at nearly the same size.

Two entries can never get an emitter under any course. Our generator declines SYS)179 and SYS)181 at all thirteen sites the manual permits them, and pays 29 extra words of object code to do it. test/fixtures/90.05-object-code-notes.md, descriptors list item 2, states the rule: "the dispatch selection rule: SYS)180 when the source is a register, SYS)182 otherwise, and never SYS)179 or SYS)181."

Why A, and what kind of decision it is

The project has stopped at the same line twice before. Stage 1 shipped its storage map with no stop shape because it could detect no error, and chunk B8 added the shape with the first diagnostic (M4-2 as amended). The SYS)162 comparison boundary stays unbuilt beside AND, OR and NOT, because no comparand in the sample passes one word (M4-11).

This is a judgment call and not a section 11 ruling. Section 11 bans code that is neither exercised nor tested. Course B would have been tested, so section 11 did not forbid it. RT-1 says so in its own words: "The narrow set is a judgment call, and Jack can overturn it. A wider set was legal." A second reviewing model, consulted on the plan before any code was written, said the same. Overturning it costs one milestone of handler writing, not a rewrite.

One consequence for M7, recorded now

No handler that a run reaches arms SYS)130. Decision record D4.2 gives that cell to nine counted overflow-test steps — SYS)195, 196, 199, 201, 203, 204, 270, 277 and 281. Our generator emits none of them, so no run has ever written the cell. The M7 diff pass must read SYS)130 as unexercised, and not as tested and found zero. D4.3 — the blank and the edit characters no longer arm the cell

D4.3 governs what a numeric handler does with a character that is not a digit: it sets communication cell SYS)131 and continues. The amendment exempts two classes. Its words, in docs/design/decisions.md: "The trigger exempts two classes of character. A blank never arms the cell, in any position. An edit insertion character never arms it either. The [J 02.05.05] field-type chart is the ground for both exemptions. It admits 'digits and leading blanks' in an external decimal field (note 3). The amendment says plainly why it is not a peer collision: "D4.3 already marks the trigger a design decision under D0.4, and it leaves 'an improper data condition' unresolved." Without the exemption the trigger would arm the cell on data the chart declares legal.

4 · Five code-generator defects the runtime exposed

These defects predate this branch. The object code was always wrong at these five sites. Nothing could see it before, because nothing ran the object code. The runtime is the first reader, and it made them visible. None is fixed on this branch, and each fix is a change to the generator, not to the runtime.

Line numbers below are as of the commit this record links to. Each site is quoted, so a later edit that moves a line still leaves the site identifiable.

The second path is external decimal to internal decimal, at procedure.dart:2026-2031, which compares nothing at all:

The generator's own third path refuses the mismatch that these two accept. _internalMove at procedure.dart:2209 throws an internal-decimal move off its trigger (catalogue 4.6) when the fraction digits differ. So the repository already holds both answers.

One correction to docs/HANDOVER.md. Its list gives the example as "MOVE NUM (999) TO EDT ($8889.99) renders 123 as $1.23" without saying what NUM is. The example holds only when NUM is an internal decimal. Defect 2 — an edited ADD source skips the scale check

_addPair at procedure.dart:2588-2591 refuses a pair of unequal scales:

The edited-source branch of _add, at procedure.dart:2526 (if (_sem(source).fieldClass == FieldClass.edited)), returns before reaching _addPair. It converts the source, parks it, and adds it to each target with no scale test at all.

Defect 3 — an S position is counted as a stored character

An S in a pictorial is a digit the field represents and does not store. The two counts differ by design. data_map.dart documents digits as "Digits the field represents, S fillers included", while pictorial.dart documents storageChars as "Storage positions: one per format character except V, S, and F".

Three call sites hand a MOVPAK handler the digit count where the handler reads characters off the source cursor: procedure.dart:2028 (_txi(184, _sem(source).digits)), :2079 (_txi(fromEdited ? 198 : 193, s.digits)), and :2557 (final int digits = _sem(source).digits;, which feeds both SYS)269 and SYS)275). With an S in the source the handler reads past the end of the field.

The generator already refuses an S in an edited target (M4-9 item (f), new on this branch). It does not refuse one in a numeric source.

Defect 4 — the SYS)184 path stores through a clobbered register

In the six lines quoted under defect 1, _loadBaseOf(target) and the store run before _movpakClears(). _movpakClears is what tells the generator that a MOVPAK call has destroyed index register 1, and _loadBase emits nothing when its cache still believes the register holds what it wants:

The conversions design pass found it and left it alone, at evidence/design-conversions.md section G.8: "Codegen observation, out of scope, no fix here. … No sample site is located on that path, so listing-diff cannot show it."

What I need from you

My recommendation: refuse all five in one follow-up pull request now, then take MOVE alignment as a generator chunk before M6's second corpus, where a program that needs it will actually exist. Keep the refusal, and annotate D2.1

M4-2 as amended is the doctrine: where the sample attests no shape, the recovery fails rather than inventing one. D2.1 gains a sentence saying the generator refuses the continue path. Honour first-wins for every duplicate label

This one breaks a locked record. The comment at the refusal site says why: "Rebinding keeps only the later address, against D2.5's section scoping". Making it keep the first binding would quietly send every reference to the second X to the first one's address, and the program would run the wrong code with no diagnostic. The honest version of this option is not "first wins" but "give the binder D2.5's scoping", which is a larger piece of work than stage 4 or this pull request.

What I need from you

My recommendation: keep the refusal and annotate D2.1. Two PROGRAM.START labels is a programmer error that the compiler already reports twice, no sample attests the continue path, and inventing object code for it would put an unattested shape into the M7 comparison.
