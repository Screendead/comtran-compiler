One answer for every open defect

Under the 2026-09-14 rule, handle wherever attested words exist, and refuse only where none do — yes or no?

“Attested words” means every word of the generated sequence occurs in the 1962 sample listing or in J 90.02, in the same role. A join between two attested words that the sample never shows is allowed; the probe runs test each join.

For yes

  • Your rule: “if it would compile in 1962, it should compile. If it wouldn't, it shouldn't.” (docs/design/m6-acceptance.md, M6-9.) All ten shapes are plain COMTRAN. F and J admit each one. A search of J 90.01 for subscript, positional, array, parenthes, nest, expression and receiving finds no restriction on any of them. So a refusal is stricter than the 1962 processor.
  • Defect 9 is the sharpest case. J 02.04.07.01 says the code for SET K=K+2 updates the indicators, and J 90.02.05 prints the words. M4-10 already orders the update “eagerly at the store site”. Today's code disagrees with its own design record.
  • The handled sequences reuse sample words. Precedent: PR #143 (comparisons) and the defects 1 and 2 prototype took the same course.

For no

  • M6-9 says whether a shape compiled, not which words it compiled to. Where the sample has no instance of the shape, the 1962 words are unknown. Evidence exists and is sealed until M7. A refusal states that gap honestly; a reconstruction can be wrong in a way M7 then has to measure.
  • Defect 10 shows the risk. There the attested words are wrong, so “attested” and “right” can part.
  • Defect 11's prototype adds no new operation or form, but the cell choice (skip a parked cell) has no instance anywhere, and RS)2 itself never prints in the sample. It is our design.

Recommendation: yes. No changes the sample or the corpus less than yes does: both leave every golden as it stands. No refuses about ten shapes that F or J show, among them the manual's own SET K=K+2. Yes keeps a refusal wherever no attested sequence exists, so the honest-gap argument still holds at those sites.

Defect 8. A subscripted MOVE target loses its subscript

_moveUnit (procedure.dart:2232) takes targetSubscripted and passes it to neither internal-decimal arm, nor to the external-to-internal arm. Each emits a plain STO CELL, so every pass writes element 1. The sample's subscripted moves are sources only.

The words the prototype uses are the comparand's, from the sample (evidence/golden-cited-words.txt):

01407  CLA 1)RATE,1      the accumulator holds a value
01410  LAC PI)1,2        the indicator into register 2
01411  TXL SYS)294,2,0   the guard on an unset indicator
01412  CAS 0,2           the element the register reaches

The prototype emits the same prologue and STO 0,r in place of CAS 0,r. LAC and TXL leave the accumulator alone, as 01407–01412 shows. For an external source the prologue follows the convert's TXI SYS)184,1,3; that join has no sample instance inferred safe, and the probe run tests it.

Refuse

Defect 9. A SET or ADD into a subscript variable moves no indicator

_subscriptRecomputation (procedure.dart:2520) has one caller, the MOVE. The manual says the update follows every change of a subscript, and names SET:

M4-10 (docs/design/m4-codegen.md) already designs it: “A SET whose target is a subscript variable updates the affected positional indicators eagerly at the store site”, a constant increment by CLA CP)+n / ADD PI)n / STO PI)n, any other store by the recomputation of LOC 01421–01425. The prototype does exactly that, after every SET and every ADD target. The DO FOR's own step at LOC 00714–00716 is the constant form. J 90.01.02 says it twice more: “When a subscript changes value, all positional indicators containing that subscript will be re-evaluated”, and, after SET I = 3, SET J = 5., “the positional indicator for A(I,J) is computed when I and J are set”.

The options

Refuse

SET and ADD into a subscript variable refuse a SET or ADD into a subscript variable (no sample instance) proposed text, not built.

Refuses J's own example. Leaves M4-10's design unbuilt while M4-10 says it is the rule. To reverse: one commit.

Handle (recommended)

Every SET (figurative fill included) and every ADD target is followed by the update. SET K = K + c, with c an integer literal and K of scale 0, takes the constant form; anything else recomputes.

Two changes for an external-decimal index. SET EXI = 3 now refuses an external-decimal subscript variable (M6-9), as a MOVE into it already did; before, it compiled and moved no indicator. SET EXI = EXI + 1 compiles to the constant form, which reads no binary index. Both are pinned (codegen_refusal_test.dart, codegen_test.dart). To reverse: delete the calls.

Defect 10. The subscript store's base drops the field's byte

The recomputation adds a base word NAME-n with a zero decrement. A reader through SYS)132 then reads from byte 0 of the word. The manual says an indicator holds the byte, and gives the base word's form with it:

The sample's own site is the problem. In TABLE.ITEM, INSPREM is at byte 0 and RETPREM at byte 3 of the element's second word (measured from our data map, evidence/sample-table-bytes.txt). The 1962 listing gives both bases the same word, 01742 PZE RETPREM-2 000000000134 and 01743 PZE INSPREM-2 000000000134. That is M6-4 finding 1, the 1962 processor's own defect, and the golden needs it. A general fix writes 000003000134 at 01742 and moves the golden. So a fix needs a boundary.

The prototype's boundary (A): a store that drives one indicator carries the byte, PZE B-2,,2, the form the DO FOR base already uses (PZE I+0,,5, M6-9). A store that drives several keeps the 1962 words. The several-indicator block is already “fitted to the one site” by M4-6's ordering rule, so the new boundary falls on an existing one. Probe D10-two shows what it costs.

The options

A. One indicator carries the byte; several keep the 1962 words (built, recommended)

Fixes every one-indicator store. A several-indicator store over a field inside a word stays wrong, silently, exactly as in 1962. A later reader must be told the boundary is fitted; the code comment says so. To reverse: one line.

B. Refuse one indicator over a field inside a word; several keep the 1962 words

Refuse a subscript-store base inside a word (no sample instance) proposed text, not built.

Turns the fixable case into a refusal and leaves the unfixable case silent. Worse than A on both counts.

D. Narrower: keep the zero decrement only where the field shares its element word with another field the same store drives

Not built. Keeps the sample (RETPREM shares its word with INSPREM) inferred, and fixes several-indicator stores whose fields sit in separate words. A more fitted rule, guessing at the 1962 mechanism, which is sealed until M7.

C. Carry the byte everywhere and move the golden

The only right answer for every program, and it breaks the oracle: 90.05-payroll.code changes at 01742, the run's RET.PREM column changes, and M6-4's finding 1 stops reproducing. HANDOVER bars it: “each fix must leave test/goldens/90.05-payroll.code as it stands”. Listed for completeness.

Defect 11. A sub-chain overwrites the outer chain's park

The arm BinaryExpr() when _additive(term) (procedure.dart:3023) calls _chain, whose cells start at 0. M4-10 rule b numbers a park by “the cell its later operands count”. Both chains apply it from 0, so the inner chain's first park lands on the outer's RS)1. Every word involved is in the sample (LOC 00621–00626: STQ RS)1+0 … STQ RS)0 / CLA RS)1 / SUB RS)0).

The prototype: a chain numbers its cells by the M4-10 rule, counted over the cells that hold no park of an enclosing chain. At the top level no cell is parked, so every existing chain keeps its numbering. That is why the golden does not move. In the probe the inner park goes to RS)2.

Rejected: offset the inner chain by the outer's term count. Section 0 reserves three cells (resultStorageCells = [3, 2, 3, 7]), so the probe's inner park would need RS)3 and refuse. Also rejected: evaluate sub-chains before the outer terms. That reorders words against M4-10's source order.

The options

Refuse

Refuse a sub-chain in a chain after a parked term (no sample instance) proposed text, not built. The truth-function case already refuses this way (an expression comparison inside a truth function after a parked term).

Refuses ordinary parenthesised arithmetic. To reverse: one commit.

Handle (recommended)

No new operation or form. The cell choice is ours and has no sample instance; RS)2 never prints in the sample. A deep nest can still run out of a section's cells, and then refuses result-storage cell n of section s (M4-10) as today. The truth-function refusal is left as it is. To reverse: revert the hunk in _chain and _park.
